# 17 — Architecture decisions

## Accepted

1. **ADR-001: PostgreSQL is authoritative.** Editorial truth, revisions, audit, source metadata and outbox live here; caches/search are projections.
2. **ADR-002: Modular monolith first.** NestJS modules share a deployable runtime and explicit boundaries; no microservices initially.
3. **ADR-003: Separate public web and newsroom.** Their security, UX and caching needs differ.
4. **ADR-004: REST-first contracts.** Use OpenAPI/typed DTOs; reserve realtime protocols for measured needs.
5. **ADR-005: Revisioned editorial model.** Published content points to an approved revision/translation; corrections create new revisions.
6. **ADR-006: Transactional outbox.** Async consumers never depend on dual writes from a request handler.
7. **ADR-007: Central AI Gateway.** Provider/model/prompt/cost/provenance policy is centralized and human approval is mandatory. Google Gemini is the initial provider, reached only through the Gateway's adapter pattern, never called directly from domain modules.
8. **ADR-008: Cloudflare R2 plus CDN.** Object storage is separate from database and public delivery is cache-friendly. R2 is confirmed over generic S3; no egress fees when paired with Cloudflare's CDN.
9. **ADR-009: Capability authorization over role branching.** Roles compose capabilities and scopes.
10. **ADR-010: Branded cards/posters are deterministic template compositing, not generative AI.** A `CardTemplate` plus a raw photo and news item text are composited by a worker job; AI may only ever suggest an input to that pipeline (crop/focal point, caption copy), never generate the base image.
11. **ADR-011: Editorial/runtime configuration is PostgreSQL-backed and admin-editable, separate from deployment config.** `packages/config` holds only environment/deployment values; policy that legitimately varies by desk, market or time (workflow rules, AI budgets, rate limits, retention, locales) is DB-backed, `config.manage`-gated, and audited. Feature flags gate risk-bearing modules independently of deploys. See [configuration and feature flags](./21-configuration-and-feature-flags.md).

## Made while implementing

These were not in the original plan. Each is built and tested; revisit one if its stated reason stops holding.

12. **ADR-012: The newsroom signs in on its server, and the browser never holds the API token (sign-in provider and session approach amended by ADR-046 and ADR-047).** Authorization code with PKCE, state and nonce; the access token sits in an encrypted, HttpOnly, SameSite=Lax cookie; the browser reaches the API only through a proxy that checks `Origin` and an allowlist. Reason: no token in page scripts, one place for CSRF defence. Initial cost: no refresh; ADR-046 later added backend-managed sessions with rotating refresh tokens.
13. **ADR-013: The worker changes domain state only through the API.** It reads the outbox and the due schedules from PostgreSQL, but publishing goes through `/internal/schedules/:id/publish`, which re-checks every rule and returns the first outcome when repeated. Reason: domain invariants stay in one place ([15](./15-repository-structure.md)). The internal surface is off without a shared secret and must stay off the public network.
14. **ADR-014: A revision is editable until it is submitted.** Submitting locks it and stores a content hash; sending a news item back, revising a published news item or correcting it opens a new revision that copies the old one. Reason: reviewed text is never changed in place (ADR-005). See [06](./06-editorial-workflow.md).
15. **ADR-015: Slugs are reserved at publish.** A slug owned by another news item fails the publish with a conflict; replaced slugs stay in a registry and redirect. Reason: drafts cannot squat on addresses, and the invariant "unique per locale" is enforced by the database.
16. **ADR-016: Uploads are untrusted bytes, and readers get only derivatives.** The type comes from the bytes, every image is re-encoded (metadata removed), variants are made during the upload, and the public route serves a derivative only for an image used by a live news item whose rights still allow the web, checked on every read. See [10](./10-media-architecture.md). Cost: variant generation is synchronous until it moves to the worker.
17. **ADR-017: SQL migrations, owned by the API.** `node-pg-migrate` with plain SQL files that have Up and Down sections; the worker's tests run the same files. Reason: the schema is the contract between apps and reads best as SQL. No ORM.
18. **ADR-018: Contracts are Zod schemas, not OpenAPI-first.** `packages/contracts` holds transport schemas and enums shared by the API and the newsroom, and a test compares each enum with its database CHECK constraint. OpenAPI generation (doc 20, Epic A) is deferred until an external client needs it.
19. **ADR-019: A fake identity provider for local work.** `tools/dev-idp` signs anyone in who clicks a name; it listens on loopback only and refuses to start when `NODE_ENV=production`. ADR-046 later selected backend-managed sign-in for staff; the fake provider remains a development and test tool.
20. **ADR-020: Languages are rows, taxonomy names are label rows.** Categories and tags are single records with a label per language (`category_label`, `tag_label`), and the supported languages are the `locale` table. Reason: the site starts in English and Bangla and more are coming; a new language must be a data change, not a schema or code change. Consequence: no language is named in the taxonomy code, and a missing label hides the item in that language ([19](./19-open-questions.md), 21).
21. **ADR-021: The domain word is "news".** The thing an editor writes and a reader reads is a `news` item, not a `story`: tables (`news`, `news_revision`, `news_translation`, `news_slug`, `news_tag`, `news_contributor`, `news_source`), `news_id` columns, capabilities (`news.edit`, `news.publish`, …), routes (`/news`, `/public/news/:locale`), events (`news.published`) and code. Screens and prose say "news item" where a count is needed. Reason: it is the term the product and cipher-press use. Migration 14 renames the schema and rewrites capabilities, configuration and queued events; audit rows are append-only and keep the old words. `apps/web` is the public design and keeps its own vocabulary.
22. **ADR-022: Writing help is a thin Gemini adapter in the API, until the AI Gateway exists.** `apps/api/src/ai` calls the Gemini API from the server (key in `GEMINI_API_KEY`, never sent to the browser) for three editor-triggered helpers: headline, standfirst, slug, search text and existing tags from a text, and translation of one language into another. Nothing is saved by the API: the editor reviews and saves. Tags are chosen only from existing active tags. Each use is audited without the text. This is not ADR-007's Gateway: there is no prompt registry, budget, cost record, provenance or approval step yet, and the unpublished text is sent to Google. Reason: editors need the help now. Revisit: when the Gateway is built, move the adapter behind it and enforce the budget; until then there is no rate limit.
23. **ADR-023: RSS feeds are fetched by the worker and stored by the API.** An administrator adds each feed address (that list is the allowlist); the worker's `feed.scan` queues `feed.fetch` for feeds that are due, fetches with conditional requests, and reports what it found to `/internal/feeds/:id/ingest`, so the API still owns every write. The fetcher only reaches public http(s) addresses: the DNS lookup of the very connection refuses private addresses (so rebinding cannot get through), numeric addresses and every redirect hop are checked, and responses are capped in time, size and type. An item is stored once per feed (`UNIQUE (feed_id, guid)`); the same canonical address already in the inbox or in the sources is stored as a duplicate, not merged. An item used for a news item becomes a `source` (`ingest_channel = 'rss'`) attached to it. Reason: docs/08's pipeline for the first connector, with the plan's SSRF rules. Not built: partner APIs, single approved URLs, Telegram, similarity-based duplicates, AI classification.
24. **ADR-024: A poll vote is one per browser, and keeps no personal data.** (Its per-address rule is amended by ADR-037.) A reader's browser gets a random token in an HttpOnly cookie from the API (relayed on the public site's own domain by its vote route); the database allows one vote per token hash per poll. The address is hashed per poll, and a vote is refused once that hash has voted on the poll (ADR-037). Hashes are keyed (`POLL_HASH_SECRET`, else derived from `INTERNAL_API_TOKEN`); with neither, voting is off. The address comes from `X-Forwarded-For` only when `TRUST_PROXY` is on, which is for an API that is reachable only through a proxy or the site. (How the address is passed on is set by ADR-048.) This stops casual and scripted repeat voting; it cannot prove one person, since clearing cookies and changing network gets another vote, and fingerprinting and sign-in were rejected (privacy, and not realistic for a news poll). Polls are written per language, a language with no question is absent from that language's site, and the wording is fixed once there are votes. The newsroom says the numbers are reader interest, not a survey. Reuses `news.edit` and `news.publish`; no new capability.
25. **ADR-025: Sections, regions and tags are three separate vocabularies, each with its own table and link table.** `category` (the news menu, with a parent, `show_in_menu` and ad targeting), `region` (the places a news item is about) and `tag` (discovery labels), each with a `*_label` table per language and a `news_*` link table; a news item has many of each (sections up to 10, tags up to 30, regions up to 20). Rejected: regions as categories with an `is_region` flag, and one generic `term` table with a vocabulary column. Reason: a region is not a menu section (the site's spec says China is a region, not a category); the flag would put a filter in every menu, section and primary-section query and let a region be a primary section or an ad target, which a foreign key cannot forbid; the two lists have their own order, addresses and pages and are likely to grow apart (a region hierarchy, country codes). Cost: a little repeated code, kept small by sharing the label helpers.
26. **ADR-026: The primary section is a flag on the link, not a second column.** `news_category.is_primary`, with a partial unique index so a news item has at most one; `news.category_id` is dropped. Reason: one source of truth; the rule "the primary is one of the sections" cannot drift. The application keeps one primary for any news item that has sections (a news item with none is allowed).
27. **ADR-027: The public address of a news item is `/story/<slug>-<id>`, and the id is the creation time.** `news.short_id` is the creation time in milliseconds since 1970 in base 36 (8 characters, `0-9a-z`), made by the database, unique, the same in every language, never changed; the next free millisecond is taken on a clash and the API retries a race. The site finds the item by the id; a wrong or old slug with a known id redirects to the current address; a bare slug still resolves. The id is not secret and shows when an item was created. Reason: the site's spec fixes the shape, and a time-based id sorts and needs no coordination.
28. **ADR-028: Old addresses of sections, regions and tags redirect, and lists are read from the link side.** Replaced label addresses are kept in `taxonomy_slug_history` (a foreign key per kind, cascade on delete) and answered with a 301 after a 404 only, so the normal path costs nothing. The public lists add only the filters asked for, as plain `EXISTS`, and the link indexes carry `news_id`, so a rare section, region or tag starts from its own index (measured on 200,000 news: a 40-item region list 73 ms to 12 ms). Not done, by design: `published_at` copied onto the link rows, a search index for the hub pages and per-key CDN invalidation; revisit with measured load.
29. **ADR-029: The site's social links and contact details are deployment settings.** `SITE_SOCIAL_*` and `SITE_CONTACT_*` in the API's environment, validated when the API starts (a social address must be https and on its network's own domain) and served read-only at `/public/site/social-links` and `/public/site/contact`. They are not edited in the newsroom and not stored in the database; migration 26 removes the old `site.social_links` configuration value. Reason: they identify the organization and change rarely and deliberately, like the other settings, so one source (the environment, reviewed with the deployment) is safer than a screen that any administrator can change, and a wrong address cannot reach the site unnoticed. Cost: a change needs a new start of the API, and the public site's cache (one minute) before it shows. A person's own social links are editorial data and stay in the database.
30. **ADR-030: Read next was specified before implementation; amended by ADR-043, which records the built feature and its final rules.** The related-news API, newsroom picks panel and public site section are built. The system ranks recent live items sharing a tag, region or section, with editorial picks first, language isolation, and opinion and author caps as described in [23](./23-read-next.md). Questions 22 to 24 in [19](./19-open-questions.md) are resolved. Revisit the ranking with measured editorial results.
31. **ADR-031: Reading time is calculated from the word count, with an optional editor override (built in steps 1 to 5).** It is worked out per language version from the body text (words counted with `Intl.Segmenter` in that language, not by spaces) at a words-a-minute rate per language kept in the runtime configuration (defaults 230 for English, 170 for Bangla, the rates the public site already uses), rounded, at least 1, and is not stored. An editor may enter a whole number of minutes (1 to 120) on the translation; blank means calculated. It is per language version because the same article takes a different time in each language. The newsroom shows the calculated value beside the field so an override cannot go stale unnoticed. Described in [24](./24-reading-time.md); built in steps 1 to 5. Question 25 is resolved: the first version includes the editor override.
32. **ADR-032: Most read is counted first-party in Redis and rolled up by the worker through the API.** The public site sends a view beacon after the page is shown; the API counts the first view of a news item, in a language, by a session in 24 hours (a Redis `SET NX` with a 24 hour expiry) into hourly sorted sets (9 days); the live ranking sums the last 24 or 168 hours (cached a minute), filters by section, region and format in PostgreSQL and widens to 7 days and then to the newest news when too few are read. The worker's `analytics.rollup` job calls `POST /internal/analytics/rollup`, and the API adds each finished hour to `news_performance_daily` (by Dhaka day, with views by source) exactly once, recorded in `analytics_flush` in the same transaction: the API owns the write, as for feeds, and the worker only schedules. Administrators read it through `analytics.read` (most and least read, views a day, per-group totals, a daily series per news item). Rejected: counting on the server render (pages are cached on the CDN, so it would miss most views), a third-party API (reporting delay and quotas), and a counter column on `news` (a hot row in the table editors use). Reason: the plan in doc 03, with the abuse resistance in doc 12. Cost and limits: reports lag by up to an hour; a news item's section is today's, not a snapshot; Redis is a hard dependency of the live ranking (a Redis outage makes the list fall back to the newest news and drops views, never errors); counting is off until the flag `analytics.news_views` is on; the public site sends the view beacon, and its homepage and category pages read the Most read list. Described in [25](./25-most-read-and-performance.md).
33. **ADR-033: A news item's lead image is its own revision media role, set through the API.** `PUT /news/:id/lead-image` sets or removes the `lead` row of the open revision (one per revision; a locked revision refuses), so it travels with the revision. Reason: the public lists and Most read need a picture, and the role existed in the schema but nothing could set it. Publishing still needs a credit or licence on every picture (existing rule); requiring a lead image to publish is open.
34. **ADR-034: Public search and trending terms were specified in a fixed order; amended by ADR-044 for the search index and opinion rule, and by ADR-045 for editorial trending.** The public search index, endpoint and reindex command are built; editorial trending terms and the `/search` results page are also built. Opinion pieces are excluded from results unless the format filter asks for them. Computed trending remains future work because search queries are not stored. See [26](./26-search-and-trending.md). OpenSearch remains deferred; see [09](./09-search-and-discovery.md).

35. **ADR-035: Branded cards render in the worker and are stored through the API.** The worker composites a card with sharp and the bundled Noto fonts, and reads and writes only through `/internal`; it never holds storage credentials or touches the card tables. The API checks the source rights on every render, requires WebP at the template size, and sets the output asset to ready once. Templates take no uploaded assets in v1, so no font or SVG upload path exists for them. Revisit when templates need their own assets or a second renderer.

36. **ADR-036: Card outputs are exempt from the unique checksum; uploads never match them.** A branded card is derived, one per request, and identified by its card, so two cards that render to the same bytes must both succeed. The checksum index is therefore a plain lookup index plus a unique index that excludes card outputs (object keys under `derivatives/cards/`). Every other asset stays unique by checksum, which the upload race handling relies on. Upload lookups exclude card outputs, so an upload never returns one. The migration down step refuses, rather than deletes, while two assets share a checksum. The partial index depends on that key prefix, so card output keys must keep it.

37. **ADR-037: Each network address votes once per poll.** The per-address daily limit of ADR-024 is replaced: the address hash may cast one vote on a poll, so a second browser from the same address is refused for that poll. The 24-hour count and `POLL_VOTES_PER_IP_PER_DAY` are removed. A browser that has voted is still recognised by its cookie. The product owner chose this rule. The trade-off: a shared network (an office, a university or a mobile carrier) gets one vote per poll in total. Revisit if readers on shared networks are refused in volume.

38. **ADR-038: The full check runs packages and database test files one at a time.** The root `test` script runs packages in sequence, and the API and worker run their database files one at a time. Parallel runs made two packages share the vitest cache and made database suites contend for one PostgreSQL, which caused random failures. The cost is a slower check (about a minute on a developer machine). Tests are not skipped or changed to pass. Revisit if the check becomes too slow, for example with a shared pre-migrated template database.

39. **ADR-039: The public-site defaults for Read next, reading time and search are approved.** The rules and weights of Read next (doc 23) are the first version. Topics are the existing tags until a topic table is approved. Opinion may appear in Read next at most once, and only when it shares a topic. Reading time ships with the editor override (doc 24). Trending starts from the editorial list, with computed terms later. Search uses `simple` with trigram matching on titles, without a Bangla dictionary, to be revisited on measured quality (doc 26). Search queries are not kept until a privacy review. Recorded here because the defaults for topics and query retention were chosen by the lead, not stated by the specs.

40. **ADR-040: The public site reads published news from the API, with these fixed choices.** The article, category, analysis and topic pages are built from the API when `FACTLENS_API_URL` is set, and from the mock content when it is not. The public news detail carries its lead image, with the same rule as the lists. The article body maps to the site's blocks: marks are dropped, and unknown nodes are logged rather than dropped silently. Reading time follows doc 24, with the default rates in the code until the runtime configuration is read. Read next is hidden in API mode until it has an API. Article addresses are generated on request in both modes. The reader figure takes a resolved image, so body pictures from the API display. Recorded because each of these is a choice the plan did not make.

41. **ADR-041: The public homepage and regions are built from the news lists, and media is served from the site's own origin.** The homepage hero, analysis and opinion, the featured Asia region and Geopolitics category, the five categories (three items each), most read and the regions with news come from the list endpoints. A section with no items is left out. The variant that the mock uses is not used in API mode. Media URLs stay relative; a Next `beforeFiles` rewrite sends `/public/media/...` to the API, and the middleware skips those paths, so they are not redirected to a language prefix. Recorded because the approved defaults and the rewrite are choices the plan did not make.

42. **ADR-042: The unavailable page answers 503, from a cached readiness check in the middleware.** With the API configured, a document request is answered with HTTP 503, retry-after 30 and the localized page while the API readiness endpoint is down. The check runs at most once every 10 seconds per process, with a 1 second timeout, and concurrent requests share it. Mock mode makes no check. A 500 would be dropped from search results, and a 503 tells crawlers to retry later. The cost is one small request every 10 seconds per process, not one per page. Checked by hand with the API unreachable (503) and in mock mode (200). Recorded because the check and its cache are choices the plan did not make.
43. **ADR-043: Read next is computed on request from a fixed pool, with these values the plan left open.** `GET /public/news/:locale/:ref/related` ranks the newest 300 live items in the locale. The recency boost is 2 for a new item and halves every 30 days, and it only orders items that already share a tag, region or section. The editor's picks bypass the opinion and author caps, because the editor chose them; they still count towards those caps for the algorithmic items. Only the `author` role counts as the author for the two-per-author cap. Nothing is cached in the database; the response carries the same 60-second public cache as the article.
44. **ADR-044: The public search document is owned by the API and written from an internal endpoint.** The worker's `search.index` job asks `POST /internal/search/:id` for an upsert or delete, as its other jobs do; it runs no search SQL itself. The API keeps one `news_search` row per live item and language (a tsvector, title weighted above body, plus a trigram index on titles), so the SQL lives in one place and is tested with the API. The choices docs/26 left open: `english` for English and `simple` for other languages; a title or body match counts when the text matches or the query matches the title with word similarity of at least 0.4; the score is text rank, plus half the title similarity, plus up to 0.2 for recency (halving every 30 days); the cursor is an offset, which is stable while the index is unchanged; opinion pieces are left out of results unless the format filter asks for them, as the public news lists do; a query over 200 characters is refused with 400, and a query under two characters returns no items. `pg_trgm` is created by the migration, so the database role needs the right to create extensions. The reindex command (`pnpm --filter @fact-lens/api search:reindex`) rebuilds every row from the stored text and is safe to run again.
45. **ADR-045: The trending terms are an editorial list per language, replaced in one audited save.** The first version of trending search terms (doc 26, section 5) is a list of up to six terms per language in `trending_term`, kept by editors with `config.manage`. A save replaces the whole list in one transaction with an audit event (`trending.update`). Duplicates are refused case-insensitively, and each term is at most 60 characters. Readers get `GET /public/trending-searches/:locale`, cached for a minute; an empty list hides the row. Computed trending terms remain the later step in doc 26.
46. **ADR-046: Sign-in and sessions are managed by the backend, not an external identity provider.** The API owns accounts, passwords (Argon2id), TOTP multi-factor sign-in with recovery codes, sessions (an 8-hour sign-in, 15-minute access tokens, single-use rotating refresh tokens with reuse detection), lockout after 5 failures in 15 minutes, and admin-issued invitations that expire after 72 hours. The newsroom signs editors in through its own page. Invitations are delivered by the admin until an email provider is chosen. Authorization (roles to capabilities, MFA checks, audit) is unchanged. The plan is docs/plans/auth-in-app.md.
47. **ADR-047: Production runs on the backend's own sign-in keys; the external provider is still trusted while it is configured.** Production refuses to start without AUTH_SIGNING_KEY, AUTH_ENCRYPTION_KEY, AUTH_ISSUER and NEWSROOM_BASE_URL. The API checks tokens from its own key and from an OIDC provider when one is configured, so the fake provider keeps working for development until the newsroom signs in itself (step A7). Keys are generated by `auth:keygen` and kept in the environment file (base64 of the PEM, so one line). The first administrator comes from `auth:bootstrap`, which prints a one-time link and refuses once an administrator exists. A new signing key signs out everyone. The newsroom (step A7) keeps the refresh token inside its own encrypted session cookie, never in the browser's reach, and sends it to the API from its server. Refresh tokens are single use, so requests that refresh at the same moment share one refresh within one process; a deployment with several newsroom instances needs a shared store for that before it scales out.

48. **ADR-048: The public site passes on the reader's address only when it sits behind its own proxy; the API uses it only behind TRUST_PROXY.** Poll votes (ADR-037) and view counts (ADR-032) apply per-address rules, but the API saw the public site's own address for every reader, or a client-chosen first X-Forwarded-For entry when TRUST_PROXY was on. The site now takes the last X-Forwarded-For entry, the one its proxy appended, and passes it on only when `SITE_TRUST_PROXY=true`; otherwise it passes no address. The API takes the address from X-Forwarded-For only when `TRUST_PROXY` is on, and then treats a request with no X-Forwarded-For as having no address, so the per-address rules are skipped rather than applied to the site's own address. Rejected: trusting the socket address behind the site (it is the site's own, so every reader shares one bucket), and a shared secret header between the site and the API (a second secret for one address). Cost and limits: the site must sit behind exactly one proxy that appends to X-Forwarded-For; with no address, votes and views are not limited per address. Sign-in, search and the newsroom's proxy still read the address the same way and are not changed here. Described in [12](./12-auth-security-and-audit.md).

49. **ADR-049: RustFS is the S3-compatible server for local development and the storage tests, in place of MinIO.** The MinIO image on Docker Hub (`minio/minio`) and the Quay copy (`quay.io/minio/minio`) can no longer be pulled anonymously, so `pnpm infra:up` and CI could not start the storage service. RustFS (`rustfs/rustfs`) speaks the same S3 API, checks request signatures (the storage tests require it, and the wrong-secret test passes), and takes the same kind of settings. The image is pinned by digest in `infrastructure/docker-compose.yml` and in CI. Rejected: a login for a registry (a secret in CI for a test server), and an S3 mock (it does not check signatures). Cost and limits: RustFS is newer than MinIO and is less established. Production still uses the configured S3 store (R2 or S3), not this server. The 6 real-S3 tests pass locally against this image; CI runs them on the same image and is not yet seen green there.

50. **ADR-050: Sign-in always counts its attempts, and search and the newsroom pass on only the address they can vouch for.** The newsroom passed on the last X-Forwarded-For entry whether or not a proxy sat in front of it, so a client without a proxy could choose its address. The newsroom now passes an address only with `NEWSROOM_TRUST_PROXY=true`. The API's sign-in, accounts and refresh endpoints take the newsroom's address when one comes, and otherwise fall back to the socket address, so an attempt is never uncounted (fail-closed). Public search takes the reader's address from the public site, the same way poll votes and view counts do (ADR-048), and skips its per-address limit when there is none (fail-open for readers). Rejected: skipping the sign-in limit when there is no address (an attacker could then remove the limit), and a single shared bucket for all searches (one busy reader would block everyone). Cost and limits: without a trusted address in front, every editor who signs in through the newsroom shares the newsroom's bucket of 20 attempts a minute; search has no per-reader limit without the site's trusted address. Redis: `REDIS_URL` is required by the environment check, so the limit is always present in production; an unreachable Redis fails the request rather than skipping the limit. Described in [12](./12-auth-security-and-audit.md).
51. **ADR-051: The cipher-press articles are imported by the seed, as news items, with a stable key and the mapping decided here.** The export in `apps/api/seed-data/legacy` (2,196 Bangla articles, 12 authors, 292 tags that the seed already had, and their links) is loaded by `pnpm seed` after the reference data. Each article is one news item with the key `legacy:article:<id>`, so a second run adds nothing (idempotent) and the import rolls back as a whole on error. The 2,186 dated articles are published at their original time and the 10 undated ones are drafts. Each article becomes one revision and one `bn-BD` translation; the legacy slug is kept, and a clash gets the legacy id appended (none occur). Plain-text paragraphs become Tiptap paragraphs and must pass the body contract; the one `<u>` span in the export becomes the underline mark. Sections map to the five site sections: International and Politics to Geopolitics, National to Security, Economy and Business to Economy, Technology to Technology, Health to History; Local, Sports, Analysis and uncategorized articles have no section (Analysis is the analysis format). Authors become contributors, matched on name so an existing one is reused. Email addresses are not in the seed copy. Published items are written to the search index with the same projection the API uses. The import writes rows directly, as the reference seed does, so it runs no publish rules and writes no audit rows, and the items have no desk. Timestamps are read as UTC, which is how Strapi stores them. Rejected: a migration per legacy row (the data is seed input, not schema), and running the import only through the API (it would need an editor's session and a publish per article). Cost and limits: the data is 16 MB in the repository; the seed takes about 12 seconds on a local database. The imported articles have no pictures, so the public article page shows a flat placeholder in the hero slot (the card placeholder style, DR-338), with no picture; the design rule that the lead image is required (spacing-layout-system §7A.5, tajmin 24 Oct 2026) still applies to new articles, and the exception needs recording in the design system by its owner. Media, legacy URL redirects, related items, featured and breaking flags, and reading-time overrides are not imported (docs/14). Described in [14](./14-data-migration-plan.md).

## Deferred with revisit triggers

- **OpenSearch:** advanced faceting/autocomplete/semantic or measured scale/latency.
- **Temporal:** long-running, durable, human-interrupted workflows that need workflow history beyond BullMQ.
- **Kafka:** high-volume replayable streams with independently operated consumers.
- **Kubernetes:** actual scheduling/autoscaling/multi-service needs beyond managed containers.
- **Microservices:** a module needs independent scaling/security/release/failure isolation and has stable contracts.
- **ClickHouse:** analytics facts and concurrency make PostgreSQL/external BI insufficient.
- **WebSocket collaborative editing:** concurrent editors require presence/real-time merging.

Each revisit must include measured load, operational cost, failure model and migration path.
